# TOOL-104：GNU Make

## 课程简介

- 来源：GNU 官方手册与社区教程综合整理（[GNU Make 手册](https://www.gnu.org/software/make/manual/))
- 先修要求：会用 GCC 编译单个源文件（`gcc hello.c -o hello`），理解“预处理、编译、汇编、链接”四个阶段大致在做什么
- 编程语言：C/C++ 为主，构建脚本使用 Makefile 语法
- 课程难度：🌟🌟
- 预计学时：基础语法与依赖规则 6 小时，能读懂并改造大型开源项目的 Makefile 另需 10 小时以上

先看一个具体问题。写 hello world 时你编辑完 `hello.c`，用 `gcc` 一条命令就能生成可执行文件，轻松愉快。可项目一旦变成上千个源文件、散落在几十个子目录里，你就得想办法把它们编译并链接到一起；如果项目完整编译一次要半小时，而你只改了一个分号，还要为这个分号再等半小时吗？

GNU Make 解决的正是这件事。它在 Makefile 里描述整个编译流程，并声明每个目标文件依赖哪些源文件与头文件，然后只重新编译你这次修改实际影响到的部分。这套增量编译的机制是所有大型 C/C++ 项目的性能基础，理解它之后，你也能明白为什么改一个头文件会让大量文件重编——因为依赖关系把影响传导开了。

学起来不难，用起来有讲究。语法本身很小，变量、规则、目标与依赖几块就够应付大部分场景；真正的功力体现在怎么把依赖写得既完整又不冗余，怎么组织多目录结构，怎么用模式规则与自动变量减少重复。这些没有标准答案，最好的办法是读优秀开源项目的 Makefile 并模仿其写法，慢慢沉淀出自己的一套模板。

自学的第一个坑是跳过依赖关系直接背语法。Makefile 的价值几乎全在依赖声明上，如果只学会写“执行这几条命令”，就等于把一个增量编译工具退化成一个命令别名。第二个坑是容忍“改了不生效”。这类现象通常是依赖缺失或时间戳问题，遇到时不要用 `make clean` 一劳永逸地绕过，应该顺着依赖链找出漏洞，否则项目稍大就会反复踩同样的坑。第三个坑是没打好 Make 基础就去上 CMake。CMake 抽象层次更高，理解 CMakeLists.txt 的生成逻辑需要先知道它最终在描述什么，先用 Make 写过几个真实的多文件项目，再学 CMake 会顺得多。

## 资源汇总

进阶练习可以从阅读出发：找一个你熟悉的中小型 C 项目，通读它的 Makefile，画出目标与依赖的关系图，再尝试删掉冗余规则、补上缺失依赖。重复几次之后，你会对“一次构建到底发生了什么”建立起完整的直觉。
