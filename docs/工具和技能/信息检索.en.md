# TOOL-109: Information Retrieval

## Descriptions

- Offered by: Community experience plus the official help pages of various search engines (the search engine principles section draws on public material)
- Prerequisites: Able to use a browser and the internet; basic English reading skills markedly improve result quality
- Programming Languages: None; this is a general-purpose skill
- Difficulty: 🌟
- Class Hour: About 5 hours to read and form the habit, then continuous refinement through daily use

When you hit a problem, read the documentation first, not the search engine, and certainly not a person. Plenty of answers sit in the FAQ, and a five-minute look can settle it. Information retrieval addresses the second layer: when the docs do not have it, how do you dig it out of a search engine accurately?

Understanding how search engines work explains why the tricks help. There are roughly three stages. Crawling and fetching, where spiders follow links, visit pages, and store HTML. Preprocessing, which extracts text, segments Chinese words, and builds indexes. Ranking, which computes relevance for your query and produces the results page. The first stage is the well-known crawler, the second is the engine's core but not critical for users, and the third concerns you directly: the form of your query decides how it is matched against the index.

Several practical principles follow. **Prefer English**: material in programming and software is generally higher quality in English, and terminology is defined in English, so translations invite ambiguity, while Chinese word segmentation is itself imprecise and whole-sentence queries often return nothing useful. **Extract keywords instead of searching sentences**: a search engine is a machine, not a colleague, so it does not infer your intent. Split "how to integrate vcpkg into a project rather than globally" into "vcpkg integrate project global" and hit rates climb. **Substitute and exclude**: swap "project" for "repository" when nothing turns up, use `-` to exclude noise words, quotes for exact matches, `filetype:pdf` to restrict file type, and `site:stackoverflow.com` to restrict the domain.

GitHub search deserves its own note: `in:name`, `in:description`, and `in:readme` scope the match, `stars:>100` filters by stars, `language:java` restricts the language, and `user:` and `org:` target specific accounts. These combine freely, and starting from the awesome list for a field often saves the most time of all.

The first pitfall is idolizing one search engine. Many people are told to avoid Baidu, but in practice Bing is not especially accurate in Chinese, Google needs network access, and Baidu indexes the most Chinese pages, so for purely Chinese problems it can actually be the best choice; keep Ecosia and Yandex around too. A search engine is a tool, and being usable and useful is the only standard, so no stance is needed. The second pitfall is avoiding specific communities. For language-level questions go to Stack Overflow with a `site:` prefix; for specific software go to its official forum or issue list; QQ groups work too but replies are slow, and only if the question is worth asking. The third pitfall is treating second-hand notes as conclusions. Chinese notes on Zhihu, Jianshu, Cnblogs, and CSDN are mostly retellings of someone else's debugging session; use them for ideas, never as authority, and always verify versions and APIs against official docs.

## Personal Resources

Local code search has its own tools: ACK is the veteran Perl implementation, The Silver Searcher is written in C and faster, The Platinum Searcher is Go-based and conveniently cross-platform, FreeCommander's built-in search is fast enough on SSDs, and IDE search wins by integrating with navigation. For open source code search, try Searchcode. Choose by a simple standard: whichever feels natural at your daily repository size.
